# 트랜잭션 경계 누수: 조건별 재고 불일치

## 왜 쟀나

2024-07 당시 테스트에서 관측된 오차는 1~3% 수준이었는데, 나중에 HTTP 부하테스트로 다시 재보니
요청의 절반 가까이가 어긋났다. 같은 버그인데 규모가 두 자릿수 배 차이가 나서 원인을 갈랐다.

## 고정 조건

- 유저 1,000명 / 쿠폰 재고 500개 (2024년 `CouponServiceDBTest` 와 동일)
- Lettuce 스핀락(15~30ms 랜덤 백오프), 트랜잭션이 락을 감싸는 구성(`txWrapped=true`)
- 서비스 메서드 직접 호출(HTTP 스택 없음), 코루틴 또는 전용 스레드풀
- 측정: 발급된 `coupon_user` 행 수 − 실제 재고 차감량

## 결과

| DB | 동시성 | 불일치 | 비율(재고 500 대비) |
|---|---|---:|---:|
| H2 인메모리 | 코루틴 `Dispatchers.IO` | 18 | **3.60%** |
| H2 인메모리 | 전용 스레드풀 1,000 | 6 | **1.20%** |
| MySQL 8.0 (fsync 2회/커밋) | 코루틴 `Dispatchers.IO` | 497 | **99.40%** |
| MySQL 8.0 (fsync 2회/커밋) | 전용 스레드풀 1,000 | 499 | **99.80%** |
| MySQL 8.0 (fsync 끔) | 코루틴 `Dispatchers.IO` | 232 | **46.40%** |
| MySQL 8.0 (fsync 끔) | 전용 스레드풀 1,000 | 283 | **56.60%** |

H2 + 코루틴 조건은 세 번 반복했고 1.60% / 1.00% / 3.60% 였다.

## 해석

새는 구간은 `락 해제 → 커밋` 하나다. 이 창이 열려 있는 동안 다음 스레드가 재고를 읽으면
차감 전 값을 본다. 따라서 창의 크기 = 커밋에 걸리는 시간이다.

- **동시성은 영향이 거의 없다.** DB 를 고정하고 코루틴 ↔ 스레드 1,000개를 바꿔도
  H2 는 3.60%↔1.20%, MySQL 은 99.40%↔99.80% 로 움직이지 않는다.
- **DB 가 결정한다.** 동시성을 고정하고 DB 만 바꾸면 3.60% → 99.40% (약 27배).
- **그중 절반 이상이 fsync 다.** `innodb_flush_log_at_trx_commit=0` + `sync_binlog=0` 으로
  끄기만 해도 99.40% → 46.40% 로 떨어진다. 남는 46% 는 fsync 를 빼고도 남는
  MySQL 의 커밋 비용(네트워크 왕복·엔진 처리)으로 보이나, 더 쪼개 보지는 않았다.

## 시사점

버그는 같은데 드러나는 정도를 실행 환경이 결정한다. 인메모리 DB 는 커밋이 즉시라
창이 거의 없고, 그래서 같은 결함이 1~3% 로만 보인다. **오차가 작게 보이는 것이
버그가 작다는 뜻이 아니다.**

## 한계

- 남은 46% 의 내역(네트워크 왕복 / 엔진 처리 / 그 밖)을 분해하지 않았다.
- MySQL 은 Docker 컨테이너이고, 호스트와의 경계 비용이 포함된 값이다.
- 재고 500 / 유저 1,000 한 조합에서만 쟀다. 재고나 요청 수를 바꿨을 때의 변화는 보지 않았다.
- H2 조건에서 한 번, 스레드풀 조건에서 `ModelNotFoundException` 이 나 회차를 버린 적이 있다
  (테스트를 연속 실행하며 유저 id 가 밀린 것으로, 수정 후 재측정했다).
